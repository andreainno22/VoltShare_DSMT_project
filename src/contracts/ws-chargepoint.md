# Contract — Charge point channel (charging hardware ↔ station)

**Status: owned by A.** Both ends are implemented by A — the `vs_cp_ws` handler and the Node.js emulator — so this file changes without a PR. It matters more than an internal protocol usually would: it is the boundary of the system (SCOPE §7). Everything above it is production logic, everything below it is emulated hardware, and the emulator is credible only if this interface is one a real charge point could implement.

The message set is a reduced **OCPP 1.6-J**: the same shape, the same direction of authority, a fraction of the surface. §8 maps every message to its OCPP original.

---

## 1. Who talks to whom

```
ws://<station-host>:8081/ws/cp?station_id=<id>&connector_id=<n>
```

The charge point is the **client** and dials the station — the same way real equipment dials the operator's backend, because the hardware sits behind NAT on a site network and cannot be dialled into. One connection per connector: it keeps the routing trivial (the socket *is* the connector) and mirrors the way a multi-outlet unit reports each outlet separately.

`connector_id` is globally unique, as everywhere else in the system (schema.sql). A connector id that does not belong to `station_id` is refused at the handshake with close code `4404`.

A second connection for a connector that already has one **replaces** it: hardware that reconnects after a network blip must not be locked out by its own stale socket. The old socket is closed with `4409`.

Frames are text, one JSON object each.

---

## 2. Envelope

Same shape as the driver channel, so one JSON codec serves both:

```jsonc
// charge point → station
{ "action": "meter", "request_id": "cp-91", "payload": { } }

// station → charge point
{ "type": "ack", "request_id": "cp-91", "payload": { } }
{ "type": "command", "request_id": null, "payload": { "command": "set_limit", "limit_kw": 60 } }
```

`request_id` is generated by the charge point and echoed. It is not a deduplication key here — the events of the two sides are naturally idempotent or naturally ordered — but it lets a log line be followed end to end, which is worth its weight when a session goes wrong during the demo.

There is **no authentication on this channel**. It is a site-local link between the controller and equipment on the same private network; in a real deployment it would be mutual TLS. Stated as an assumption rather than pretended away.

## 3. Bring-up

### 3.1 `boot`

First frame after connecting, before anything else:

```json
{ "action": "boot", "request_id": "cp-1",
  "payload": { "vendor": "VoltShare-Emu", "model": "EMU-150", "firmware": "0.1.0",
               "rated_kw": 150, "status": "available" } }
```

The station replies with everything the charge point needs to behave, so that the equipment carries no configuration of its own:

```json
{ "type": "ack", "request_id": "cp-1",
  "payload": { "accepted": true, "heartbeat_interval_s": 30, "meter_interval_s": 5,
               "server_time": 1755790000000, "limit_kw": 0 } }
```

`accepted: false` with a `reason` means the station does not recognise this connector; the charge point closes and retries with backoff.

**Booting resets nothing.** A charge point that reconnects sends `boot` again and reports its true physical `status`; the station reconciles that against what it believes (§6). The hardware is the authority on what is plugged in, the station is the authority on what is authorised — keeping those two straight is the whole difficulty of this interface.

### 3.2 `heartbeat`

```json
{ "action": "heartbeat", "request_id": "cp-42", "payload": {} }
```

Every `heartbeat_interval_s`. The `ack` carries `server_time`, which the charge point uses to keep its clock aligned; timestamps that matter for billing are always taken by the station, never by the equipment.

Three missed heartbeats and the connector is marked `out_of_service`: it disappears from the driver's view, cannot be reserved, and any reservation on it is released with a `session_interrupted` notification. Charging that was in progress is closed with the energy last reported — a session that cannot be measured must not keep accruing cost.

## 4. Events from the charge point

### 4.1 `status`

```json
{ "action": "status", "request_id": "cp-7",
  "payload": { "status": "available" } }
```

`available` \| `occupied` \| `faulted` \| `unavailable`. Sent on change. `faulted` immediately takes the connector out of service and stops any session; the driver is notified with `session_interrupted`.

### 4.2 `plugged`

The event that starts everything:

```json
{ "action": "plugged", "request_id": "cp-8",
  "payload": { "vehicle_id": 88, "soc_pct": 22, "battery_kwh": 58, "max_kw": 150 } }
```

The charge point identifies the vehicle — in real equipment this is Autocharge or ISO 15118 plug-and-charge, here it is a field in the emulator. The station then authorises, and this is the only place where authorisation happens:

| Connector state | Vehicle | Outcome |
|---|---|---|
| `held` | matches the reservation | session starts, lease cancelled, claim kept until the session ends |
| `held` | different vehicle | refused: `command / stop` with reason `not_your_reservation`; the reservation stays |
| `free` | any | **walk-in**: session starts against that vehicle's account, no claim needed |
| `free`, account suspended | any | session starts anyway — the penalty suspends reserving, not charging (SCOPE §3.3) |
| `charging` \| `closing` | any | refused, `invalid_state`; the physical state and ours have diverged, and the station logs it loudly |

The battery figures come from the vehicle, not from the account: `battery_kwh` and `max_kw` drive the charging curve and cap the allocation, so a 50 kW car never receives a 150 kW share that would be wasted on it.

### 4.3 `meter`

```json
{ "action": "meter", "request_id": "cp-9",
  "payload": { "power_kw": 89.4, "energy_kwh": 12.317, "soc_pct": 58 } }
```

Every `meter_interval_s` while charging. `energy_kwh` is **cumulative since the session started** and monotonic: the station stores `max(stored, reported)` so that a meter that resets on a firmware glitch cannot subtract energy already billed. `power_kw` is what is actually flowing, which may be below the allocated limit when the car itself is tapering — that difference is what makes the redistribution in the station manager worth doing.

A `meter` for a connector with no session is dropped and logged; it means the two sides disagree and the next `status` will resolve it.

### 4.4 `unplugged`

```json
{ "action": "unplugged", "request_id": "cp-10",
  "payload": { "energy_kwh": 41.203 } }
```

Ends the session: the station writes the `sessions` row with the final energy and any overstay, releases the claim, returns the power to the pool and moves the connector to `free`. `unplugged` on an idle connector is ignored — it is the harmless half of a divergence.

## 5. Commands from the station

Always server-initiated, `request_id: null`. The charge point applies them and reflects the result in its next `meter` or `status`; it never argues.

```json
{ "type": "command", "request_id": null,
  "payload": { "command": "set_limit", "limit_kw": 60 } }
```

| Command | Payload | Meaning |
|---|---|---|
| `set_limit` | `limit_kw` | ceiling for this connector, recomputed on every arrival, departure and tick (SCOPE §3.5). `0` means suspended: the session stays open and draws nothing |
| `stop` | `reason` | end delivery now. Reasons: `driver_stopped`, `target_reached`, `claim_revoked`, `not_your_reservation`, `station_shutdown`, `faulted` |

`set_limit` is sent on every recomputation even when the value is unchanged; it is cheap, and it means a charge point that missed a frame is corrected within one tick rather than staying on a stale limit. Idempotence by repetition is easier to reason about than delta tracking, and this channel has no ordering problem to justify the alternative.

The charge point must apply a new limit within `LIMIT_APPLY_SECONDS`. Nothing enforces that here — real hardware ramps — but the emulator honours it, and the demo's power scenario is timed against it.

---

## 6. Reconciliation

The interesting failure is a station that restarts while cars are plugged in — station autonomy (SCOPE §4) means the hardware carries on delivering power meanwhile.

1. The charge point notices the socket is gone and reconnects with backoff (1 s, doubling, capped at 30 s).
2. It sends `boot` with its true `status` and, if a session is running, a `plugged` with the vehicle and the cumulative energy it has counted.
3. The station has no memory of the session — the connector processes died with the node — so it adopts what the hardware reports: it opens a session from the reported figures rather than stopping a car that is charging happily.
4. Energy delivered before the crash is preserved, because the charge point counts it, not the station. The session row is written when the car unplugs, with the meter's total.

What is deliberately *not* attempted: reconstructing the reservation. The claim expired or belongs to a new leader's table, and re-deriving it would mean trusting hardware on a question hardware cannot answer. The car keeps charging, the session is billed, the reservation is gone.

The mirror case — the charge point disappears while the station lives — is §3.2: three missed heartbeats, connector out of service, session closed with the last measured energy.

---

## 7. Behavioural rules

1. **The station authorises, the charge point reports.** Equipment never decides who may charge; it says what happened and applies what it is told.
2. **The hardware is authoritative on physical state**, the station on authorisation. Every reconciliation follows from this split.
3. **Energy is cumulative and monotonic.** Never a delta, never allowed to decrease.
4. **Timestamps that matter are the station's.** The charge point's clock is a convenience.
5. **Limits are repeated, not diffed.** A missed `set_limit` self-corrects on the next tick.
6. **Divergence is logged, never silently patched.** A `meter` without a session or a `plugged` on a charging connector points at a real bug, and the log line is how it gets found during the load tests.

## 8. Mapping to OCPP 1.6-J

Useful in the report: it shows the reduction is a subset, not an invention.

| This contract | OCPP 1.6-J | What was dropped |
|---|---|---|
| `boot` | `BootNotification` | vendor-specific configuration keys |
| `heartbeat` | `Heartbeat` | — |
| `status` | `StatusNotification` | the nine-state model reduced to four; no error codes taxonomy |
| `plugged` | `Authorize` + `StartTransaction` | id tags and the local authorisation cache; identification is by `vehicle_id` |
| `meter` | `MeterValues` | the sampled-value matrix reduced to three measurands |
| `unplugged` | `StopTransaction` | transaction data records |
| `set_limit` | `SetChargingProfile` (smart charging) | profiles, schedules, stacking levels — a single instantaneous limit remains |
| `stop` | `RemoteStopTransaction` | — |
| — | `DataTransfer`, `FirmwareUpdate`, `Reset`, `UnlockConnector` | out of scope: operations, not coordination |

The one structural difference: OCPP 1.6-J multiplexes every connector of a unit over one socket with a `connectorId` field, while here each connector has its own socket. It costs a few file descriptors and buys a direct mapping from socket to owning process, which is the shape the actor model wants.

## 9. Example — a session with contention

```
CP conn3                                       station1
   |  boot {rated_kw:150, status:"available"}      |
   |---------------------------------------------->|
   |  ack {heartbeat_interval_s:30, limit_kw:0}    |
   |<----------------------------------------------|
   |  plugged {vehicle_id:88, soc:22, max_kw:150}  |
   |---------------------------------------------->|  connector held by vehicle 88 → authorised
   |  command {set_limit, limit_kw:150}            |  350 kW site budget, only car on site
   |<----------------------------------------------|
   |  meter {power_kw:148.2, energy_kwh:2.4}       |
   |---------------------------------------------->|
   |                                               |
   |                       (a second car plugs into connector 1)
   |  command {set_limit, limit_kw:175}            |  budget split; both below their rating
   |<----------------------------------------------|
   |  meter {power_kw:150.0, energy_kwh:9.1}       |  capped by the car's own 150 kW
   |---------------------------------------------->|
   |                                               |
   |  meter {power_kw:41.0, energy_kwh:38.7}       |  battery above 80 %, car tapers
   |---------------------------------------------->|  freed headroom returns to the pool
   |  unplugged {energy_kwh:41.2}                  |
   |---------------------------------------------->|  sessions row written, claim released
```

## 10. Configuration

| Variable | Default | Meaning |
|---|---|---|
| `CP_WS_PORT` | `8081` | listener port inside the container |
| `CP_HEARTBEAT_INTERVAL_S` | `30` | heartbeat period handed to the charge point at boot |
| `CP_HEARTBEAT_MISSED` | `3` | missed heartbeats before `out_of_service` |
| `METER_INTERVAL_S` | `5` | meter period handed to the charge point at boot |
| `LIMIT_APPLY_SECONDS` | `5` | window within which a new limit must be honoured |
| `MIN_CHARGE_KW` | `6` | below this the session is suspended (`set_limit 0`) rather than starved |
| `OVERSTAY_GRACE_SECONDS` | `300` | after charging completes, before the overstay charge starts |
