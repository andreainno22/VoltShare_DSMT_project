# Contract — Reservation claim (station ↔ coordinator)

**Status: frozen after joint review. Changing this file requires a PR reviewed by both developers.**

This is the mechanism that enforces the system's central invariant: *a vehicle holds at most one active reservation across the whole network* (SCOPE §5, P2). The station asks, the coordinator decides.

Owners: **A** implements the caller (`vs_claim_client`), **B** implements the server (`vs_coord_srv`).

---

## 1. Who talks to whom

Every station node knows the coordinator cluster from configuration:

```
COORD_NODES=vs@coord1,vs@coord2,vs@coord3
```

**Every node in the cluster uses the same short name, `vs`** — it is the hostname that tells
them apart, and on a compose network each service already resolves the others by service name
(`deploy/docker-compose.yml` sets `NODE_SNAME: vs` everywhere). Short names throughout: mixing
`-sname` and `-name` in one cluster is the classic way to get nodes that cannot see each other.

Only one coordinator serves at a time. The station does not need to know which: it addresses the last known leader, and any coordinator that is not serving replies with a redirect (§4).

The coordinator process is a `gen_server` **registered locally as `vs_coord_srv`** on each coordinator node. Messages are sent to `{vs_coord_srv, Node}`.

All calls are `gen_server:call/3` with a **2000 ms timeout**. A timeout is treated exactly like an unreachable node (§5).

---

## 2. Types

```erlang
-type vehicle_id() :: pos_integer().
-type user_id()    :: pos_integer().
-type station_id() :: pos_integer().
-type conn_id()    :: pos_integer().    %% globally unique, not per-station
-type claim_id()   :: binary().         %% opaque, generated by the coordinator
-type req_id()     :: binary().         %% generated by the station, echoed back
-type epoch_ms()   :: pos_integer().    %% erlang:system_time(millisecond)
```

`claim_id` is opaque to the station: it must be stored and returned, never parsed.

---

## 3. Messages

### 3.1 Acquire

Sent **before** the station commits a reservation. Never the other way round (DESIGN-NOTES §3).

```erlang
%% request
{claim, ReqId :: req_id(), VehicleId :: vehicle_id(), UserId :: user_id(),
        StationId :: station_id(), ConnId :: conn_id()}

%% replies
{ok, ReqId, ClaimId :: claim_id(), GrantedAt :: epoch_ms(), ExpiresAt :: epoch_ms()}
{error, ReqId, already_held | suspended | rebuilding | unknown_station}
{not_serving, LeaderNode :: node() | undefined}
```

| Reply | Meaning | What the station does |
|---|---|---|
| `ok` | the vehicle is now committed to this station | commit the reservation, arm the lease |
| `already_held` | the vehicle holds a claim elsewhere | refuse, error code `NO_CLAIM` to the driver |
| `suspended` | the account is serving a no-show penalty (SCOPE §3.3) | refuse, error code `SUSPENDED` |
| `rebuilding` | a new leader is still rebuilding its table | refuse, ask the driver to retry in a few seconds |
| `unknown_station` | the coordinator does not know this station yet | refuse; the station re-announces itself and retries once |
| `not_serving` | this coordinator is not the leader | retry on `LeaderNode` (§4) |

`ExpiresAt` is always **longer than the reservation lease** — the coordinator grants `lease + 60 s` — so a claim never expires while the reservation it protects is still alive.

**`GrantedAt` is issued by the coordinator, never by the station.** The station stores it and
echoes it back in `renew` and in `who_do_you_hold`. The reason is the ordering rule in §5: if
each side produced its own timestamp, "oldest wins" would compare clocks belonging to machines
that were never synchronised, and a conflict would be decided by the drift between them. With
the value coming from one place, the ordering holds regardless — including across a failover,
because the new leader adopts the timestamp rather than inventing one.

### 3.2 Renew

The station renews **all** its claims every **10 seconds**, in one message. Renewal is what allows a new leader to learn about claims it never granted (DESIGN-NOTES §4).

```erlang
%% request
{renew, StationId :: station_id(),
        Claims :: [{claim_id(), vehicle_id(), conn_id(),
                    UserId :: user_id(), GrantedAt :: epoch_ms()}]}

%% reply
{renewed, Ok :: [claim_id()], Revoked :: [claim_id()], NewExpiresAt :: epoch_ms()}
{not_serving, LeaderNode}
```

Both extra fields travel with **every** renewal, not only the first, because a renewal is how a
leader learns about claims it never granted:

- `GrantedAt` — the timestamp this claim was born with, so that "oldest wins" (§5) has something
  to compare. Without it a newly elected leader would have to invent one, and adoption would
  silently reset the ordering.
- `UserId` — so that a leader adopting a claim can enforce a suspension straight away, instead
  of holding a claim it cannot attribute until the next `who_do_you_hold`.

A claim in `Revoked` is **no longer valid**. The station must, for each revoked claim: cancel the reservation or stop the session, free the connector, and notify the driver with the reason `claim_revoked`. This is not an error path to be logged and ignored — it is how the system converges after a conflict.

A renewal for a `claim_id` the coordinator has never seen is **accepted**, not rejected: the leader adds it to its table with the `GrantedAt` the station reports. This is the case of a claim granted by the previous leader.

### 3.3 Release

```erlang
%% request — fire and forget, no reply expected
{release, ClaimId :: claim_id(), Reason :: cancelled | expired | completed | revoked}
```

Sent when the driver cancels, when the lease expires without the vehicle arriving, when a charging session ends, and after processing a revocation. Losing a release message is harmless: the claim expires on its own.

### 3.4 Rebuild query

Sent by a newly elected leader to every known station. The station replies with everything it currently holds.

```erlang
%% request (coordinator → station, to registered name vs_claim_client)
{who_do_you_hold, From :: pid(), CoordNode :: node()}

%% reply
{holds, StationId :: station_id(),
        [{VehicleId, UserId, ConnId, ClaimId, GrantedAt :: epoch_ms(), ExpiresAt :: epoch_ms()}]}
```

The station answers **immediately** from memory, without touching the database. `GrantedAt` is the timestamp the coordinator returned when the claim was first acquired; the station stores it for exactly this purpose.

Transport, unlike the messages above: this one is a **plain message** to the registered name
`vs_claim_client` on the station node, and the answer is a plain message back to `From` — not a
`gen_server:call`. The rebuilding leader is talking to several stations at once and must not
block on any of them; a station that never answers simply does not contribute to the rebuild,
and the collection timeout closes the round.

### 3.5 Station announcement

Sent by the station on start-up and every 30 s, so the coordinator can keep the cluster map and feed the back office.

```erlang
{station_up, StationId, Node :: node(), Name :: binary(), WsUrl :: binary(),
             SitePowerKw :: pos_integer(), TariffCentsKwh :: pos_integer(),
             Connectors :: [{conn_id(), RatedKw :: pos_integer()}]}

{station_stats, StationId, Free :: non_neg_integer(), Held :: non_neg_integer(),
                Charging :: non_neg_integer()}
```

The coordinator also sets a `monitor_node/2` on every announced station, so it detects a crash without waiting for the next announcement.

## 4. Finding the leader

The station keeps `current_leader` in the state of `vs_claim_client`, initially the first entry of `COORD_NODES`.

1. Send to `{vs_coord_srv, current_leader}`.
2. On `{not_serving, LeaderNode}` with a node: set `current_leader = LeaderNode` and retry **once**.
3. On `{not_serving, undefined}`, on timeout, or on `noproc`: try the next node in `COORD_NODES`, round-robin, at most one full pass.
4. If a full pass fails: give up, refuse the reservation with `NO_CLAIM`, and retry the discovery on the next request. **Do not queue and do not block the connector process.**

Discovery failures must never stop charging sessions already in progress: they only prevent new reservations.

---

## 5. Behavioural rules

Binding on both sides — these are the guarantees the design rests on.

1. **Claim first, commit after.** A station never moves a connector to `held` before receiving `ok`. A crash between the two leaves an unused claim, which expires; the reverse order would leave a reservation nobody knows about.
2. **No claim, no reservation.** If the coordinator is unreachable, reservations are refused. Walk-in charging on a free connector is still allowed — it needs no claim.
3. **The coordinator serves only when it is leader and in quorum.** In any other state it replies `not_serving` or `{error, _, rebuilding}`, never a grant.
4. **Revocation is authoritative.** The station obeys a revocation immediately, even if it believes the claim is valid.
5. **Oldest wins.** If two stations renew claims for the same vehicle, the coordinator keeps the one with the smaller `GrantedAt` and revokes the other.
6. **Releases are best-effort.** Correctness never depends on a release arriving; expiry is the backstop.

## 6. Example — the happy path

```
station1                                     coord2 (leader)
   |  {claim, <<"r-91">>, 88, 12, 1, 3}          |
   |-------------------------------------------->|   vehicle 88 free → grant
   |  {ok, <<"r-91">>, <<"c-4f2a">>, 1755...}    |
   |<--------------------------------------------|
   |  connector 3: free → held, lease 15 min     |
   |                                             |
   |  {renew, 1, [{<<"c-4f2a">>, 88, 3, 1755...}]}  |  every 10 s
   |-------------------------------------------->|
   |  {renewed, [<<"c-4f2a">>], [], 1755...}     |
   |<--------------------------------------------|
   |                                             |
   |  vehicle plugs in, charges, unplugs         |
   |  {release, <<"c-4f2a">>, completed}         |
   |-------------------------------------------->|
```

## 7. Example — failover mid-reservation

```
station1                        coord2 (dies)        coord3 (elected)
   |  {renew, ...}                   X                     |
   |-------------------------------->                      |
   |  (timeout 2000 ms)                                    |
   |  try coord3                                           |
   |  {renew, 1, [{<<"c-4f2a">>, 88, 3, 1755...}]}         |
   |------------------------------------------------------>|  unknown claim,
   |                                                       |  accepted with its GrantedAt
   |  {renewed, [<<"c-4f2a">>], [], ...}                   |
   |<------------------------------------------------------|
   |  reservation survives; the driver notices nothing     |
```

## 8. Configuration

| Variable | Default | Used by |
|---|---|---|
| `COORD_NODES` | `vs@coord1,vs@coord2,vs@coord3` | station |
| `CLAIM_CALL_TIMEOUT_MS` | `2000` | station |
| `CLAIM_RENEW_INTERVAL_MS` | `10000` | station |
| `CLAIM_GRACE_SECONDS` | `60` | coordinator — added to the lease when granting |
| `LEASE_SECONDS` | `900` | station — shortened to ~30 s for the demo |
